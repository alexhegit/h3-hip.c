# R9700 (gfx1201) performance analysis — where the remaining time is, 2026-11-07

Branch `r9700` at `8990547` (merged into `main` as `7a9e823`). One Radeon AI
PRO R9700, `HIP_VISIBLE_DEVICES=0`, default INT8 DiT. Numbers come from
`--profile`, `rocprofv3 --kernel-trace --memory-copy-trace`, a WMMA / copy
microbenchmark, `rocm-smi` under load, and the timings in
[`R9700_2026-11-06.md`](R9700_2026-11-06.md). Nothing here changes code.

## Hardware ceilings, measured

| quantity | measured | note |
|---|---:|---|
| BF16 / FP16 WMMA, sustained 2 s | **202 / 207 TFLOP/s** | 37 ms bursts read 119–185 while clocks ramp; spec ~191 dense |
| FP8 / INT8 WMMA, sustained | **395 / 391 TOPS** | 2× BF16 |
| VRAM copy (read + write) | 475 GB/s | simple copy kernel |
| Host → device, pinned | **7.1 GB/s** | see PCIe below |
| NVMe read, `O_DIRECT` | 5.5 GB/s | |
| Board power under SDPA | 296–300 W | at the 300 W maximum `PPT0` limit; sclk ~2.70 GHz, junction 94–95 °C |

**PCIe.** The card and its first bridge run PCIe 5.0 x16, but the root port
above them (`00:01.1`, AMD Phoenix GPP bridge) is PCIe 4.0 **x4**. Every
upload — weight load and the `H3_INT8_HOST` per-block copy — is capped near
7–8 GB/s by the host, not by the code.

**Power.** Long DiT attention runs at the 300 W cap. Work that does not
reach the matrix units (softmax VALU, conversions) costs clock speed, not only
issue slots.

number. Against the sustained 202 TFLOP/s it is ~38 %.

## Where the seconds go

linear 168), video VAE 21.7 s (linear 13.8 of it), load and text ~35 s.

1344×768 · 15 s dense, 2788 s E2E: denoise 2579 s (SDPA 2264, linear 244,
other ~70), video VAE 163 s, load ~45 s.

1344×768 · 5 s, 2 steps, `H3_INT8_HOST=1`: denoise 92.1 s wall, 79.6 s GPU.
Inside the block loop each block uploads ~368 MiB of INT8 weights in
**53 ms** (6.9 GB/s), serialised against compute; the GPU is idle **7.5 %**
of the loop.

Load, fox-s2 (36 s E2E, 1.2 s denoise): text encoder ~11 s for 46.9 GiB,
DiT load ~30 s (AdaLN precompute 7.6 s, core 15–20 s for 52 GiB of BF16
weights read, uploaded, then quantized on the GPU), video VAE 3 s.

## Opportunities, ranked by value

Estimates are arithmetic on the profiles above, not measured results.

| # | change | numerics | where it pays | estimate |
|---|---|---|---|---|
| 1 | **SDPA softmax VALU diet.** Convert P without the NaN-checking `h3_f32_to_bf16` (P is finite; use a packed hardware conversion if gfx12 has one — not checked); mask only the last key tile; fold `scale·log2e` into one multiply; keep P in registers instead of the LDS round trip (S^T / O^T formulation) | first two bit-identical; last two change bits | every long canvas; SDPA is 81 % of 1344×768 · 15 s denoise | SDPA 1.3–1.6× → 1344×768 · 15 s −20 to −27 % E2E |
| 2 | **Double-buffer the `H3_INT8_HOST` slot** (copy block N+1 while block N runs) | bit-identical | 1344×768 · 5 s and every 768p LoRA run; +0.37 GiB VRAM | −7 % denoise at 1344×768 · 5 s (~150 s of 2205); ~1 % at 15 s |
| 3 | **Video VAE linear.** Convert VAE weights to BF16 once at load (the kernel already rounds them), let producers write BF16 inputs; or hipBLASLt BF16→F32 | load-time BF16: bit-identical; hipBLASLt: changes bits | all canvases; VAE weights 9.4 → ~5 GiB | VAE −30 to −60 % (1344×768 · 15 s: 163 → ~70–110 s) |
| 4 | **Load path for short clips.** Cache the GPU-quantized INT8 DiT core on disk (18 GiB instead of 52 GiB BF16 read + upload), cache AdaLN precompute per schedule, cache prompt embeddings per prompt hash | bit-identical | fox-s2, fox-fast, any repeated prompt; `--serve` already keeps weights warm | fox-s2 36 s → ~12–15 s |
| 5 | **Grouped FC2.** Exact options are exhausted (int32 planes must round-trip). Per-row FC2 activation scales would run the 222 TOPS plain GEMM | changes bits (quality check needed) | 832×480 and 864×480 canvases | −8 % E2E at 832×480 · 5 s |
| 6 | **Fuse INT8 epilogues and quantizers** (scale / SwiGLU epilogue into the next quantize, vectorise `groups_scalar`) | can stay bit-identical | all canvases | −3 to −5 % denoise |
| 7 | **INT8 VAE on hipBLAS.** `H3_INT8_VAE=1` is lossy (41.0 dB / SSIM 0.969 vs default) and today slower (26.5 vs 21.7 s) because it runs the sudot4 `t128` kernel | opt-in lossy | users who already accept INT8 VAE | VAE −50 % with that flag |
| 8 | **Text encoder GEMV** (`h3_linear_bf16_kernel`, ≤64 rows) on a WMMA / hipBLAS path | changes bits | every run, mostly hidden behind the 47 GiB load | ~2 s per run |
| 9 | **FP8 attention** (2× WMMA) | lossy | only after #1; SDPA is VALU-bound today, so FP8 alone moves little | — |

Not worth pursuing on this box:

- `H3_GPU_SAMPLER=1`: fox-fast denoise 8.4 → **11.6 s** and a different md5.
- `H3_INT8_VAE=1` as it stands: slower (row 7).
- Power and clocks: the 300 W cap is already the maximum the board allows.

## Platform notes

- Moving the R9700 to a CPU-attached PCIe 5.0 x16 slot would lift uploads
  from 7 GB/s to the 40–50 GB/s range. That would shrink load time,
  the `H3_INT8_HOST` copies, and the value of opportunity #2.
- `--vsa` at 1344×768 · 15 s does not fit in 32 GiB
  ([`../KNOWN_ISSUES.md`](../KNOWN_ISSUES.md) KI-006).

## Suggested order

1. #2 and the bit-identical half of #1 and #3: no quality review needed, md5
   gates already exist. **Done 2026-11-08, see below.**
2. The rest of #1: needs a PSNR pass versus dense on the four canvases.
3. #4 if short-clip latency or batch throughput matters.
4. #5, #7, #9 only with a quality budget.

## Implemented 2026-11-08 (bit-identical)

- **#2** `H3_INT8_HOST=1` parks the INT8 linears in one pinned arena and
  alternates two device slots: block N+1 copies on a second stream while
  block N runs, ordered by GPU events. `H3_INT8_HOST_OVERLAP=0` restores the
  single synchronous slot.
- **#1, exact half** In the gfx12 SDPA kernel, P is rounded to BF16 without the
  NaN test (P is finite), and only the last key tile is masked. SDPA bench:
  32k tokens 402 → 386 ms, 109334 tokens 4450 → 4263 ms, same output hash.
- **#3, exact half** Video VAE block weights are stored as BF16 at load (the
  WMMA kernel already rounded them per call). The linear time did not move
  (13.8 → 13.7 s on 832×480 · 5 s): that kernel is bound by the F32
  activation side, not the weights. The VAE peak dropped 9.4 → 5.1 GiB.

## Video VAE encoder (first/last frame), 2026-11-08 (bit-identical)

Found while chaining shots with `--first-frame` (864×480 · 5 s, FastH3
4-step). Encoding the one conditioning frame took **177.8 s of a 284 s run**.
Two causes:

- Encoder activations came from `h3_gpu_tensor_new_f32`, which always returns
  pinned host memory, so every conv read and wrote over PCIe x4. They now use
  `h3_gpu_tensor_new_f32_device` like the audio VAE (177.8 → 122.3 s).
- `h3_conv3d_f32_kernel` is one thread per output with a strided weight walk.
  The tiled kernel (64 out channels × 64 positions per block, 16-channel LDS
  slices, weights transposed per call into a reusable scratch) keeps the same
  per-output `fmaf` order. `H3_CONV3D_TILED=0` restores the old kernel.

| run | encoder | E2E | md5 |
|---|---:|---:|---|
| before | 177.8 s | 283.9 s | `26f911fd…` |
| device activations | 122.3 s | 230.8 s | `26f911fd…` |
| + tiled Conv3d | **2.4 s** | **108.0 s** | `26f911fd…` |

fox-s2 stays `6d17f81a…`. Ref2VA video references use the same encoder and
should gain the same way; not measured (no Ref2VA weights on this box).

## Video VAE BF16 activations, 2026-11-08 (bit-identical)

The second half of #3. The block RMSNorms and SwiGLU now write BF16 directly
when the next linear (QKV, FC1, FC2) has a BF16 weight, rounding with the
same `__float2bfloat16` the WMMA kernel applies when it loads F32 inputs. The
linear then copies both operands into LDS unchanged. The attention output
projection (fed by SDPA) and the final LayerNorm/projection stay F32.
`H3_VAE_F32_ACT=1` restores the F32 activations. INT8 VAE and the ISAs
without the WMMA F32 path keep F32 weights, so they never take it.

| 832×480 · 5 s, 4 steps, back to back | VAE total | VAE linear | VAE peak | md5 |
|---|---:|---:|---:|---|
| `H3_VAE_F32_ACT=1` | 21.67 s | 13.65 s | 5.12 GiB | `58e3c5ed…` |
| BF16 activations | **16.90 s** | **9.18 s** | 5.16 GiB | `58e3c5ed…` |

fox-s2 / fox-fast stay `6d17f81a…` / `c36b933c…`; `hip-test` passes;
`h3_kernels*.hip` compile for gfx1151, gfx90a and gfx942.
