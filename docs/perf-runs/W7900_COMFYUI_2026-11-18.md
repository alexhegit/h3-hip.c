# ComfyUI node on the W7900 (gfx1100) — 2026-11-18

The R9700 checks from [`docs/wiki/ComfyUI.md`](../wiki/ComfyUI.md) "Checked",
repeated on the Radeon Pro W7900 (45 GiB usable, 61 GiB RAM, weights on a
7200 rpm disk). Branch `comfyui` from main `22d4877`.

Setup: ComfyUI 0.44.0 (`fca60fe`) in a venv with PyTorch 2.10.0+rocm7.0
(its own ROCm runtime; ComfyUI reports 46064 MB VRAM, `cuda:0`), node linked
into `custom_nodes/h3-hip`. Daemon:

```bash
HIP_VISIBLE_DEVICES=0 H3_FFMPEG=/usr/bin/ffmpeg H3_DISK_CACHE_DIT_INT8=1 H3_CACHE_MAX_GIB=60 \
H3D_FASTH3_LORA=/DATA/HF_MODEL/FastH3-4-step-LoRA/dense-datafree/adapter_model.safetensors \
  ./h3 -d /DATA/HF_MODEL/MiniMax-H3 --serve
```

The daemon turns on `H3_INT8_HOST=1` itself on this 45 GiB card.

## Found

- **`~/.h3d` was never created.** `h3d_config.c` made `outputs`, `media`
  and `logs` with one `mkdir` each, so on a machine that never ran the
  daemon all three failed and every job got `500 cannot create the job
  output directory`. The R9700 already had `~/.h3d`, and
  `serve_regression.sh` creates its own roots. Fixed on this branch: the
  roots are created with their parents.
- **Cancel does not interrupt loading.** The worker sets the stop flag at
  once but only checks it between phases, so a cancel during the DiT load
  waits for the load to finish. On this disk that is ~500 s cold, and the
  first `serve-regression` run failed its 300 s "running job cancels" wait.
  It passed with `H3_DISK_CACHE_DIT_INT8=1`, which shortens the load. Not
  fixed here; the same applies to Interrupt in ComfyUI during load.
