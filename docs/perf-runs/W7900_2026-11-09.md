# Radeon Pro W7900 (gfx1100) — bring-up, 768p 15 s, and what moved it

2026-11-06 to 2026-11-09, branch `w7900`. One AMD Radeon Pro W7900 (Navi 31,
gfx1100, 96 CU, wave32, 48 GB GDDR6 of which 45.0 GiB is usable to HIP,
241 W board power cap), Ryzen 9 7900X, 61 GiB RAM, ROCm / HIP 7.14. The box
also has a Raphael iGPU (gfx1036), so every run sets `HIP_VISIBLE_DEVICES=0`.

This is not a `bench/` scoreboard row and not a release number. It records
why the first W7900 run took 16.8 hours, the fixes, the SDPA and INT8 work on
top, and the attempts that did not pay off.

## Fixture

Every timed row is the `bench/fox-15s.sh` prompt at the released max canvas:

```bash
HIP_VISIBLE_DEVICES=0 H3_FFMPEG=/usr/bin/ffmpeg \
./h3 --profile -d /DATA/HF_MODEL/MiniMax-H3 -p "$(cat fox-15s-prompt.txt)" \
  --width 1344 --height 768 --seconds 15 \
  --steps 20 --layers 45 --reuse 2 --seed 42 -o out.mp4
```

362 frames, 15.08 s, 109,334 packed DiT tokens, 11 DiT evaluations (495
attention calls), default INT8 DiT, no GPU sampler, no INT8 VAE. Process E2E
is `/usr/bin/time` to the muxed MP4. Weights sit on the root filesystem, an
HGST HUS726T4TALE6L4 spinning disk; the machine's SN850X NVMe is unmounted.

Machine-specific setup, not code defaults:

- The ROCm 7.14 install has runtimes but no `-dev` headers and no rocWMMA,
  and `/opt/rocm` is read-only. The Makefile falls back to a sibling
  `../rocWMMA` checkout (tag `rocm-7.2.4`) and an extract of
  `amdrocm-runtime-dev7.14` / `amdrocm-blas-dev7.14` in `../rocm-7.14-dev`
  (`01c2d5f`).
- `~/.local/bin/ffmpeg` has no libx264; `H3_FFMPEG=/usr/bin/ffmpeg`. The first
  dense run lost its MP4 to `Unrecognized option 'preset'` after 16.8 h.

## Root cause 1: DiT activations in pinned host memory

`*_device` allocations only went to VRAM when free VRAM minus the request
stayed above `H3_DEVICE_WEIGHT_RESERVE_GIB` (20 GiB on discrete GPUs). The
reserve exists to keep room for activations, but `allocate_activations()`
went through the same check. An allocation trace (temporary, not committed)
on the 768p fixture:

| | VRAM | pinned host |
|---|---:|---:|
| free after DiT weights | 27.40 GiB | |
| activations, bring-up | 8.03 GiB | **19.71 GiB** |
| activations, `a1696eb` | 23.36 GiB | 0 |

From `key` onward every activation buffer fell back to host memory, so each
SDPA and INT8 GEMM read it over PCIe. `tests/bench_kernels.hip` reproduces it:

| test | device memory | pinned host memory |
|---|---:|---:|
| SDPA, L=109334, scaled to 56 heads | 7.8 s/call, 44.1 TFLOPS | **93.0 s/call**, 3.7 TFLOPS |
| INT8 GEMM qkv / fc1 / fc2 shapes (n=8192) | 104–121 TOPS | 1.8–2.0 TOPS |

46032 s / 495 calls is 93 s per call, the host-memory figure. Raw hardware
was fine: 732 GB/s device read, 621 GB/s D2D copy, 26.3 TFLOPS FP32 FMA.
With K/V in host memory the profile shows mclk idling at 96 MHz because
nothing reads VRAM; that is a symptom, not a DPM problem, and forcing the
performance level is not needed.

`a1696eb` adds `h3_gpu_set_activation_arena()`: while on, `*_device`
allocations keep only a 256 MiB margin. The quantized QKV path also reuses
the idle `dit->qkv` buffer as `int8_qkv_ws` (4.38 GiB), which is what makes
23.36 GiB fit beside the weights with 4.66 GiB to spare.

## Root cause 2: hipBLAS INT8 at 109k rows

`h3_int8_hipblas_linear` allocated one I32 scratch of rows × out × 4 bytes
(11.7 GiB for fc1) and launched its epilogue with `grid.y = rows`; HIP caps
`grid.y` at 65535 on this device. Either failure returned 0 and fell back
to the custom kernel after the GEMM had already run. `ee1d885` chunks rows
to at most 32768 and ~1 GiB of scratch per block. At 70000 rows, qkv and
fc1 match the custom kernel bit for bit and run at 83–85 TOPS against 33–36.

The bring-up `--token-reduction` MP4 (38302 s) decodes to block noise. Use
the `tr-vram` and later TR clips; the bring-up TR is a timing only.

## SDPA on gfx1100 (`be9c03f`)

Default d128 path: `h3_sdpa_bf16_wmma_d128_kernel<8, 32>`, the wave32
rocWMMA flash kernel probed on gfx1151. The existing tile sweep at
L=109334 put 8 waves × BK 32 first (43.4 TFLOPS), 16×32 equal, everything
else 23–41 TFLOPS. Changes, measured one at a time at L=109334, 8 heads
(run-to-run spread ±0.3%):

| change | TFLOPS | kept |
|---|---:|---|
| baseline | 43.4 | |
| pad P rows to BK+8 | 42.9 | kept (no cost) |
| row max / sum via DPP `row_xmask` instead of `__shfl_xor` (ds_swizzle / ds_bpermute) | 49.3 | yes |
| stage V transposed in LDS, 4×4 register transpose | 52.0 | yes |
| P to bf16 without the NaN select | 53.2 | yes |
| prefetch next K/V tile into registers | 54.3–54.8 | yes |
| native WMMA builtin, 16-wide LDS loads per lane | 47.9 | no |
| native WMMA builtin, 8-wide loads + `v_permlanex16` | 53.4 | no |
| skip `alpha` rescale when the wave's alpha is all 1 | 54.3 | no |
| unguarded full-tile prefetch path (910 vs 1063 loop instructions) | 54.1 | no |

56 heads: 53.8 TFLOPS. Every kept step leaves the result bit-identical, and
the Sol-Attn keep-all check against dense still reports 0 diffs. Final
kernel: 222 VGPR, 29 KB LDS, six waves per SIMD.

rocWMMA on gfx11 keeps 8 k values per lane and fills the other 8 with
`ds_swizzle` at MMA time; lanes 16–31 hold k 8–15 then k 0–7. A native
builtin fed in that order is bit-identical to rocWMMA; fed in natural
order it is not (51/256 values differ in a 16×16 tile). Loading all 16 per
lane doubles LDS traffic and was slower than the swizzle.

Ceiling: under load the card holds ~2.13 GHz at the 241 W cap (which is
also `power1_cap_max`). 96 CU × 512 bf16 FLOP/clk × 2.13 GHz ≈ 105 TFLOPS,
so the kernel runs at ~52% of WMMA peak. WMMA and the softmax VALU share
one SIMD pipe on RDNA3; more lossless headroom here is small.

## Grouped INT8 GEMM (`bd209a7`)

fc2 (k=14336) and the attention output (k=7168) quantize activations per
1024-wide group, so they run 14 / 7 k=1024 GEMMs. At 109k rows the batched
path was disabled (768 MiB scratch cap) and the per-group loop reread the
I32 plane and read-modify-wrote an F32 partial per group. Per fc2 call:
GEMM 328 ms + epilogue 167 ms before; GEMM 311 ms + one reduce 63 ms after.

| shape (rows 109334) | per-group loop | batched per row block |
|---|---:|---:|
| fc2 | 443 ms, 38.0 TOPS | 326 ms, 51.7 TOPS |
| attention out | 178 ms, 47.6 TOPS | 129 ms, 65.2 TOPS |

The first version reduced with `fmaf(v, sa·sb, t)`. That changed 0.007% of
the bf16 outputs and, after 45 layers × 11 evaluations, gave a different
sample (20.07 dB against the previous dense clip). The committed reduce
repeats the loop's arithmetic with `#pragma clang fp contract(off)` and is
bit-identical (0 / 587,779,584 values), so the dense md5 does not move.
Shapes small enough for the existing 768 MiB batched path never reach the
new code.

Built before the reduce-order fix above; timings are unaffected, and PSNR
is FFmpeg `psnr` against the dense clip from the same build.

|---|---:|---:|---:|---:|---:|---:|
| dense | 5171 s | — | 4012 s | 3370 s | 576 s | — |
| `--token-reduction` | **3571 s** | −31% | 2401 s | 1928 s | 414 s | 17.2 dB |
| `--fbc` (6 full, 5 skipped) | 3785 s | −27% | 2629 s | 1834 s | 741 s | **19.2 dB** |

Same ordering as MI300X at this canvas: TR fastest, Sol-Attn closer to

FastH3, VSA, TAEH3, and Pika were not run.

## Tried and rejected

- **hipBLASLt INT8.** A standalone probe with constant (memset) data and
  unchunked n=109334 showed 92–93 TOPS against rocBLAS's ~83. Inside h3
  with random data and row chunks it was slower: qkv 63.7 vs 81.8, fc1
  64.3 vs 82.4, fc2 56.0 vs 51.5, out 58.0 vs 64.8 TOPS. Constant data
  draws less power and clocks higher; do not benchmark GEMMs with memset
  inputs on this card.
- **Composable Kernel `DeviceGemmMultipleD_Wmma_CShuffleV3`, INT8.** With the
  CK example's validated gfx11 config (256 threads, 128×128×64) and random
  data: qkv 81.9 vs rocBLAS 100.2, fc1 79.5 vs 88.5, fc2 group 76.3 vs
  81.3 TOPS. Larger tiles were rejected by `IsSupportedArgument`. A fused
  dequant epilogue would save at most ~60 s per dense run.

## Where the remaining time is

Final dense, 5171 s: weight reads ~960 s (19%), SDPA 3370 s (65%), INT8
linear 576 s (11%), video VAE 192 s, rest ~70 s.

- Weight reads: the text encoder pulls 47 GiB in ~445 s (~108 MB/s) from the
  spinning disk, and 61 GiB of RAM cannot cache the ~107 GiB read per run.
  Moving the weights to NVMe, or caching the INT8-quantized DiT and text
  encoder so each run reads half the bytes, are the largest lossless items.
- SDPA: the only large lever left is lossy, e.g. INT8 QKᵀ (RDNA3 INT8 WMMA
  is 2× bf16), with PV kept in bf16.

None of the changes on this branch were timed on gfx1151, gfx1201, gfx90a,
or gfx942. The SDPA kernel compiles for all four. The activation-arena and
INT8 chunking changes run on every ISA; check `hip-test` and the fox-s2 md5
on MI300X and Halo before merging.
